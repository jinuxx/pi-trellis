# 质量规范

## 必须遵守的模式

- 新增公开接口时，沿用相邻 Controller 的 API 文档、参数校验和响应封装。
- Controller 保持薄层，业务规则和跨表写入放在 Service。
- 使用项目已有的异常、响应、分页、权限、数据范围、密码和配置工具。
- Request、Entity、DTO/VO、数据库字段和 OpenAPI 描述使用一致的业务术语。
- 多步骤写入遵循项目事务约定，并验证回滚和重复提交行为。
- Mapper/XML、迁移、Entity 和接口改动必须同步检查，不能只修改其中一层。
- 保留 legacy API 路径、包名和兼容行为，除非任务明确要求变更。

## 禁止或高风险模式

- 没有搜索现有实现就新建工具、常量、服务、Mapper 方法或响应类型。
- 在 Controller 中写业务判断、SQL 或事务编排。
- 忽略权限、租户、数据范围、逻辑删除或敏感字段保护。
- 捕获异常后静默返回成功。
- 为无关代码做格式化、重命名、配置升级或生成文件提交。
- 只验证正常路径，不验证空值、空列表、重复操作、越权和外部失败。

## 测试与验证

根据项目实际构建方式运行最小相关检查，通常包括：

```bash
mvn test
mvn -DskipTests package
```

必要时增加模块级测试、数据库迁移检查、API 手工验证或外部接口模拟。测试应验证行为和跨层契约，而不是只验证私有实现细节。

## 代码审查清单

- [ ] 改动位于正确的 Maven module 和 feature/package。
- [ ] 已搜索并复用了已有实现。
- [ ] Controller、Service、Repository、Mapper 的职责没有混用。
- [ ] 输入校验、响应封装、权限和数据范围与相邻接口一致。
- [ ] Entity、Mapper、XML、表字段和逻辑删除语义一致。
- [ ] 分页、空集合、事务、异常和日志行为安全。
- [ ] 敏感数据没有泄露。
- [ ] 有针对改动行为的测试或可复现的手工验证。
- [ ] Diff 不包含无关文件、生成物、IDE 文件和格式化噪音。

## 代表性判断

当新增接口需要读取列表并写入关联数据时，先确认列表是否需要分页和数据范围过滤，再由 Service 负责资源校验、事务和映射；不要把查询、权限和写入全部堆在 Controller 中。
