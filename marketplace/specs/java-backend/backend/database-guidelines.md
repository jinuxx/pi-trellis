# 数据库规范

## 适用范围

涉及 Entity、Mapper、Mapper XML、SQL、分页、逻辑删除、事务、表结构或迁移时使用本规范。

## Entity 与表映射

- 先阅读目标表的现有 Entity、基类、Mapper 和查询，再决定新增字段或映射方式。
- 沿用项目已有的主键、审计字段、逻辑删除字段和填充器语义。
- 数据库表和列使用项目统一的 snake_case；Java 属性使用 camelCase。
- 计算字段、关联展示字段和其他非持久化属性必须使用项目约定的非持久化标记。
- 不要为了方便修改已被接口、脚本或其他模块依赖的字段名。

## 查询规则

- 优先使用项目已有的 BaseMapper、Mapper 扩展和 Lambda/参数化 Wrapper；不要重复实现已有默认方法。
- 所有外部输入使用参数绑定、Wrapper 或 Mapper 参数，禁止字符串拼接 SQL。
- 简单查询使用注解或 Wrapper；复杂聚合、动态条件、批量 `IN` 和多表查询放在约定的 Mapper XML 中。
- 手写 SQL 必须显式检查逻辑删除、租户和数据范围条件；不要假设 ORM 会替 XML 自动补条件。
- 列表接口保持稳定排序和分页；复用项目统一分页参数、默认值和上限。
- 空 `IN` 列表必须在 Service/Repository 提前处理，不能生成无效或全表查询。

## 多表查询与分页性能

- 项目存在 MyBatis 或 MyBatis-Plus 时，多表关联任务在满足性能的前提下优先在 Mapper/Mapper XML 中编写 SQL 联查，不要先分别查询再在内存中拼接结果。
- 允许使用 `JOIN`，但单条 SQL 最多关联 3 张表；超过 3 张表时必须重新拆分查询、建立专用查询模型或先取得必要主键后再分步查询，并说明性能依据。
- 绝对禁止逻辑分页。分页必须下推到数据库，使用 MyBatis-Plus `Page`/`IPage` 或项目现有的物理分页机制，让 SQL 生成 `LIMIT`/`OFFSET`（或等价数据库分页语句）。禁止先查出全量数据后使用 `subList`、`stream().skip/limit` 等方式在内存中分页。
- 能够在 SQL 中表达的筛选条件必须写入 `WHERE`、`JOIN ... ON` 或参数化查询条件中；禁止先查询全部记录，再在 Java 内存中比较、过滤或判断。
- 联查、过滤和分页字段必须检查索引、执行计划和返回数据量；不能仅因为 SQL 能执行就忽略性能验证。

## 事务与数据范围

- 多表写入、状态变更和需要原子性的业务流程由 Service 统一控制事务。
- 详情、修改和删除操作先加载目标记录，再校验资源存在性、权限和数据范围。
- 列表、详情、统计、导出和写操作都必须沿用项目现有的数据范围/租户边界。
- 缓存失效和审计行为遵循项目已有提交时机；不要让非核心审计失败破坏核心业务，除非业务契约明确要求强一致。

## 迁移与结构变更

修改表结构前：

1. 搜索基线 SQL、迁移目录、Entity、Mapper、XML、接口和读取该字段的业务代码。
2. 确认部署环境实际执行迁移的方式，不假设 Flyway 或其他工具一定启用。
3. 新增版本迁移，不修改已发布的历史迁移。
4. 同步更新 Entity、Mapper、查询、响应和相关测试。
5. 检查索引、唯一约束、逻辑删除、审计字段和旧数据兼容性。

## 常见错误与验证

| 变更 | 必须验证 |
|---|---|
| 新增字段 | 迁移、Entity、Mapper、响应和旧数据行为一致 |
| 新增列表接口 | 数据范围、逻辑删除、稳定排序、分页和空结果 |
| 新增批量查询 | 参数绑定、空列表、去重、数量上限和 SQL 执行计划 |
| 跨表写入 | 事务回滚、重复提交和部分失败行为 |
| 修改逻辑删除/状态 | Wrapper、XML、统计和详情查询全部保持一致 |
| 新增索引/唯一约束 | 现有数据、并发写入和重复键错误可诊断 |

## 禁止做法

- 在启动代码或业务请求中临时建表。
- 修改已经发布的迁移文件以“修复历史问题”。
- 使用字符串拼接把请求参数写入 SQL。
- 在 XML 查询中遗漏逻辑删除、租户或数据范围条件。
- 用数据库异常替代 Service 层的资源、权限和业务校验。
