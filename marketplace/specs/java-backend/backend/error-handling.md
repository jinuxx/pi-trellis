# 错误处理

## 统一流程

Controller、Service 和全局异常处理器必须沿用项目现有的响应封装和异常映射。新增接口不得创建第二套响应结构或在每个 Controller 重复实现通用异常转换。

```text
请求参数 → Controller 结构校验 → Service 业务校验
→ Service/Repository 执行 → 全局处理器转换为统一响应
```

## 校验边界

- Controller/Bean Validation 负责必填、格式、长度、类型和请求结构。
- Service 负责资源存在性、状态、重复、权限、数据范围和跨字段业务规则。
- 进入 Mapper 前确认必要参数已完成 null、格式、范围和资源校验。
- 关键业务约束不能只依赖前端校验或数据库异常。

## 异常处理规则

- 预期的业务拒绝使用项目已有的业务失败返回或业务异常，遵循相邻 Service 的约定。
- 需要全局处理的失败抛项目已有异常类型，让全局处理器统一记录和返回。
- 仅在能够重试、转换外部错误、降级或允许非核心操作失败时局部捕获异常。
- 捕获异常后必须明确记录、转换或降级；禁止吞异常、记录后继续返回成功或返回 null 伪装失败。
- 不要在 Controller 中手写通用异常响应，除非项目已有明确的绕过机制，例如文件下载或特殊协议。

## 外部服务失败

外部接口调用必须区分：

- 参数或业务拒绝：返回项目统一的业务失败结果。
- 可恢复网络/单资源失败：按既有重试、告警或降级约定处理。
- 解析失败、鉴权失败和系统性失败：保留诊断上下文，不能静默当作成功。
- 非核心通知、审计或缓存失败：只有在项目契约允许时才降级继续。

## 对外响应安全

客户端消息不得暴露：

- 数据库、SQL 和内部路径。
- 密码、Token、Cookie、验证码和第三方凭据。
- 完整堆栈和内部实现细节。

服务端日志应保留足够的关联标识，例如异常 UUID、请求 URI、业务 ID 或外部请求 ID。

## 验证矩阵

| 情况 | 处理要求 |
|---|---|
| 请求格式错误 | 使用 Bean Validation 或项目统一参数错误响应 |
| 资源不存在 | 在 Service 明确判断并返回统一业务错误 |
| 无权限或越权 | 使用项目统一的认证/授权异常映射 |
| 重复数据 | 保留统一重复错误，不直接暴露数据库异常 |
| 外部服务失败 | 区分可恢复、业务失败和系统性错误 |
| 未知异常 | 交给全局处理器，生成关联标识并记录堆栈 |

## 反例

```java
// 错误：吞掉失败并返回成功
try {
    service.save(request);
} catch (Exception ignored) {
}
return Result.ok();
```

```java
// 正确方向：使用项目已有的异常或失败返回，并让统一处理器负责响应
if (resource == null) {
    throw new ExistingBusinessException("资源不存在");
}
```

具体异常类和响应类必须替换为目标项目已有实现，不要新增单点异常体系。
