# 代码复用思考指南

## 问题

复制实现会导致：

- 一个缺陷需要在多个位置修复。
- 相同输入在不同模块产生不同结果。
- 校验、常量、字段映射和响应契约逐渐分叉。
- 新代码绕过已有权限、日志、分页或异常处理。

## 写新代码前先搜索

至少搜索以下内容：

1. 相同或相近的方法名、业务名和字段名。
2. 相同职责的 Controller、Service、Mapper、Repository 和工具。
3. 相同异常、响应、分页、校验、常量和 DTO/VO 映射。
4. 相关测试、迁移、配置和调用方。

搜索结果必须用于决定“复用、修改已有实现，还是新增实现”，不能只作为形式检查。

## 常见重复模式

- 复制一份参数校验函数，只改一个字段。
- 多个 Service 分别实现相同状态判断。
- 多处复制字典、状态、时间或业务单位常量。
- 多个接口重复从同一外部 payload 提取字段。
- 多个 Controller 手写相同错误响应、分页或权限判断。

## 什么时候抽象

适合抽象：

- 逻辑已经在两个或更多调用方共享。
- 逻辑复杂，重复实现容易产生缺陷。
- 业务契约要求所有调用方保持完全一致。
- 修复必须同时传播到所有使用者。

暂不抽象：

- 只有一个调用方，且差异可能继续扩大。
- 抽象只减少几行代码，却增加参数和间接层。
- 两段代码只是表面相似，业务语义不同。

## 批量修改后

- 重新搜索原字段、旧方法名和相同逻辑，确认没有遗漏。
- 检查所有调用方的输入、输出、异常和权限语义。
- 确认是否应该把新逻辑下沉到已有的 Service、Mapper 或 common/base 能力。

## 提交前清单

- [ ] 已搜索相似实现。
- [ ] 没有复制本应共享的契约逻辑。
- [ ] 常量只定义在一个职责明确的位置。
- [ ] 相同模式使用相同的错误、日志、分页和测试方式。
- [ ] 新抽象有真实的第二个使用者或明确的契约收益。
